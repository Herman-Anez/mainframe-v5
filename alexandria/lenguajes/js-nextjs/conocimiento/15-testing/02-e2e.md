# Pruebas End‑to‑End (E2E)

## 1. Herramientas

Las pruebas E2E simulan un usuario real interactuando con la aplicación completamente desplegada. Las herramientas más utilizadas con Next.js son:

- **Playwright**: moderno, rápido, soporta múltiples navegadores, y tiene integración con Vercel y Next.js.
- **Cypress**: popular, ecosistema amplio, pero más pesado y con limitaciones en algunas funcionalidades (como múltiples pestañas).

Recomendación actual: **Playwright** por su rendimiento, capacidad de testing de Server Components (puede esperar a que la hidratación termine) y su integración con el App Router.

## 2. Configuración de Playwright

### Instalación

```bash
npm init playwright@latest
```

Esto instala los navegadores, crea `playwright.config.ts` y una carpeta `tests/`.

### Configuración típica para Next.js

```typescript
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test'

export default defineConfig({
  testDir: './e2e',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 1 : undefined,
  reporter: 'html',
  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
  ],
  webServer: {
    command: 'npm run build && npm start',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
})
```

El `webServer` compila e inicia la aplicación antes de las pruebas.

## 3. Pruebas básicas de navegación y renderizado

```typescript
// e2e/home.spec.ts
import { test, expect } from '@playwright/test'

test('la página principal muestra el título', async ({ page }) => {
  await page.goto('/')
  await expect(page).toHaveTitle(/Mi App/)
  await expect(page.getByRole('heading', { name: 'Bienvenido' })).toBeVisible()
})
```

Para aplicaciones con i18n y prefijo de locale, usa la URL completa (`/en` o `http://localhost:3000/en`).

## 4. Probando flujos de autenticación

```typescript
test('puede iniciar sesión con credenciales', async ({ page }) => {
  await page.goto('/login')
  await page.fill('input[name="email"]', 'test@example.com')
  await page.fill('input[name="password"]', 'password')
  await page.click('button[type="submit"]')
  await page.waitForURL('/dashboard')
  await expect(page.getByText('Bienvenido test')).toBeVisible()
})
```

Para proveedores OAuth, puedes simular el flujo usando fixtures o mockeando la API de NextAuth.

## 5. Probando Server Components y streaming

Playwright espera automáticamente a que la red se calme y los elementos sean visibles. Para componentes que se cargan con streaming (Suspense), puedes esperar por un selector específico:

```typescript
await page.waitForSelector('[data-testid="heavy-content"]')
```

O simplemente `await expect(page.getByText('Contenido cargado')).toBeVisible()` que internamente espera.

## 6. Probando navegación SPA

Next.js con App Router navega del lado del cliente cuando usas `Link`. Playwright sigue la navegación sin recargar la página.

```typescript
test('navega a about y mantiene el layout', async ({ page }) => {
  await page.goto('/')
  await page.click('a[href="/about"]')
  await expect(page).toHaveURL('/about')
  // Verifica que el layout sigue presente (ej. header)
  await expect(page.getByRole('link', { name: 'Home' })).toBeVisible()
})
```

## 7. Probando Server Actions y mutaciones

Puedes probar formularios que usan Server Actions. Asegúrate de esperar la actualización de la UI.

```typescript
test('crea un post y lo muestra en la lista', async ({ page }) => {
  await page.goto('/posts')
  await page.click('a[href="/posts/new"]')
  await page.fill('input[name="title"]', 'Mi nuevo post')
  await page.click('button[type="submit"]')
  await expect(page).toHaveURL('/posts')
  await expect(page.getByText('Mi nuevo post')).toBeVisible()
})
```

## 8. Mocking de APIs externas en E2E

Playwright tiene una potente API de intercepción de red (`page.route`). Puedes simular respuestas de APIs.

```typescript
test('muestra datos mockeados', async ({ page }) => {
  await page.route('**/api/posts', (route) =>
    route.fulfill({
      status: 200,
      contentType: 'application/json',
      body: JSON.stringify([{ id: 1, title: 'Mock Post' }]),
    })
  )
  await page.goto('/')
  await expect(page.getByText('Mock Post')).toBeVisible()
})
```

Esto es útil para aislar el frontend de servicios externos inestables.

## 9. Pruebas con diferentes viewports y dispositivos

En la configuración puedes definir proyectos para mobile y desktop.

```typescript
{
  name: 'Mobile Chrome',
  use: { ...devices['Pixel 5'] },
}
```

En el test:

```typescript
test('menú móvil se abre', async ({ page }) => {
  await page.setViewportSize({ width: 375, height: 812 })
  await page.goto('/')
  await page.click('button[aria-label="Abrir menú"]')
  await expect(page.getByRole('navigation')).toBeVisible()
})
```

## 10. Pruebas de rendimiento y accesibilidad

Playwright se puede integrar con `@playwright/experimental-ct-react` (para componentes) y con librerías de a11y como `axe-core`. Sin embargo, lo más común es usar Lighthouse en CI.

## 11. Ejecución en CI

En GitHub Actions (ejemplo):

```yaml
- name: Install dependencies
  run: npm ci
- name: Install Playwright browsers
  run: npx playwright install --with-deps
- name: Run E2E tests
  run: npx playwright test
```

## 12. Buenas prácticas

- Escribe tests independientes y aislados. Cada test debería poder ejecutarse solo.
- Usa `beforeEach` para resetear el estado (por ejemplo, limpiar base de datos en entorno de testing).
- No dependas de tiempos fijos (`sleep`); usa esperas automáticas (`toBeVisible`, `waitForURL`).
- Estructura los tests por flujos de usuario (login, checkout, creación de contenido).
- Aprovecha la traza de Playwright (`trace: 'on-first-retry'`) para depurar fallos.
- Ejecuta los tests en modo headless en CI, pero también en desarrollo con `npx playwright test --ui`.
- Mantén una base de datos de prueba separada o usa contenedores Docker con Postgres/MySQL para los tests que requieren persistencia.

Con estos dos bloques, el testing de una aplicación Next.js queda completamente cubierto, desde la verificación de funciones individuales hasta la experiencia completa del usuario en múltiples navegadores.
